# QuadFlow — agent guide to this repository

QuadFlow is a Tauri v2 desktop app (AGPL-3.0) for running several AI coding agents side by side in a
tiled terminal layout, next to project tools. The repo is the app **and** its first-party plugins:
a small core (terminals, agents, layout, settings, one data layer, a `quadflow` CLI) plus plugins
for every tool (Ideas, Issues, Plans, Scripts, Ship, Chat, Missions, GitHub, Editor, …) and every
agent integration (Claude Code, Codex).

Binding design docs: `docs/ROADMAP.md` (product source of truth) and `docs/architecture/`
(`data-layer.md`, `plugin-system.md`, `agent-providers.md`). Contributor setup: `CONTRIBUTING.md`.
Plugin author docs: `docs/plugins/`. Releases: `docs/RELEASING.md`.

## Layout

```
src-tauri/quadflow-core/   Rust lib + CLI (`quadflow-core`): the ONLY place data, schemas and logic live
  src/store/               per-project `.quadflow/` files (atomic writes, advisory lock) + app SQLite (`app_db.rs`)
  src/domains/             ideas, issues/, plans/, discovery, scripts, environments, ship/, chat/, missions/, app/
  src/events/              in-process bus, `.quadflow/` watcher, app_changes cursor → `DataChanged`
  src/plugins/             manifest + schema, registry, permissions, host API dispatch (host/), sidecars,
                           CLI contributions (cli.rs), sources/install/update (sources/), asset routes
  src/agents/              agent-provider framework: spec, detect, catalog, launch builder, sessions, scaffold
  src/context/             agent context docs registry + CLAUDE.md / AGENTS.md managed-region writer
  src/cli/                 clap tree (`quadflow ideas|issues|plans|…|plugins|docs|context`)
src-tauri/src/             the Tauri shell: PTYs (terminal.rs), windows, `commands/` (thin typed wrappers),
                           bindings.rs (tauri-specta registry), plugin_host/ (terminals, native, sidecars),
                           plugin_protocol.rs (`qfplugin://`), diagnostics, updater, git worktrees, titles
src/                       React shell (Zustand stores, mosaic layout, terminals, settings, onboarding, palette)
  plugins/                 plugin host: registry, loader (trusted + sandboxed), TileHost, hostApi/, tools.tsx
  plugins/core/            UI module of the built-in `core` plugin (see below)
  components/tools/        generic tool hosts (tile content, flyout, toolbar, config modal, Tools menu)
  generated/bindings.ts    generated by tauri-specta — never edit by hand
  lib/core/                small typed helpers over `commands.*` (project open, errors)
packages/                  plugin-api (types + definePlugin), ui (@quadflow/ui kit + tailwind preset),
                           plugin-kit, plugin-build, plugin-runtime (sandbox), sidecar SDKs, create-quadflow-plugin
plugins/<id>/              first-party plugins (`quadflow-plugin.json`, src/, docs/agent.md, optional sidecar/)
plugins/index.json         the official plugin source (generated at release time)
catalog/models.json        agent model catalog (fetched by the app from the default branch)
scripts/                   build/check/release scripts; scripts/ui/ = GUI harness + e2e tests
```

Cargo workspace root is the repo root (`target/` there). `src-tauri` is package `quadflow-tauri`;
`quadflow-core` also builds a standalone `quadflow-cli` binary. Rust plugin sidecars are workspace
members; `plugins/local-titles/sidecar` is a standalone crate (llama.cpp) outside the workspace.

## Core concepts

- **One data layer.** GUI (Tauri commands), CLI and plugins (host API) all call `quadflow-core`.
  Project content lives in `<project>/.quadflow/` (one JSON file per entity, shareable via git;
  `.quadflow/local/` is machine state, gitignored). User/app state (projects registry, workspaces,
  tiles, tool configs, settings, chat, agent sessions, plugin state) is one SQLite DB
  `<appData>/quadflow.db`. Changes from any process arrive as `DataChanged` events.
- **Types are generated.** `specta` + `tauri-specta` write `src/generated/bindings.ts` and
  `packages/plugin-api/src/generated/types.ts` (`cargo test -p quadflow-tauri --test export_bindings`).
  `npm run check` fails on drift. specta exports everything into one TS namespace: prefix new type
  names with their domain (`PlanStatus`, not `Status`).
- **Everything is a plugin.** A plugin's manifest declares tiles, toolbar items, commands, palette
  providers, settings pages, CLI subcommands, agent context docs, agent providers, permissions and a
  sidecar. Bundled first-party plugins run *trusted* in the host document (sharing React via an
  import map + `public/qf-shared/` shims); everything else runs in a sandboxed iframe over RPC. One
  Rust dispatch table enforces permissions for UI, sidecars and CLI. Plugins import nothing from
  `src/` — only `@quadflow/plugin-api`, `@quadflow/ui`, `react`, `zustand` and what they bundle.
- **The `core` plugin** (`plugins/core`, "QuadFlow Core") holds the shell's own contributions: the
  Terminal and AI Agent toolbar items, the session History flyout and the commands
  `core/new-terminal` / `core/launch-agent`. It is internal: its UI module ships in the host bundle
  (`src/plugins/core/`, `INTERNAL_MODULES` in `src/plugins/loader.ts`).
- **Tools.** A tool config (`tool_configs`) points at a plugin contribution
  (`pluginId` + `contributionId`); `src/plugins/tools.tsx` derives icon, modes and behaviour from the
  manifest and `activateTool()` is the single entry point. Layout leaf ids: `term:<uuid>`,
  `tool:<ulid>`, `empty:<ulid>` (`src/lib/layoutIds.ts`).
- **Projects and workspaces.** A project is a working directory (switching changes the terminals'
  cwd); a workspace is a saved layout of terminals and tiles inside it.
- **Agents are plugins.** Providers (Claude Code, Codex) are declarative manifest specs interpreted by
  core plus optional hooks. Core and shell must not contain agent-specific literals
  (`scripts/check-agent-literals.mjs` enforces it).
- **Optional plugins** (`quadflow.bundle: "none"` in their `package.json`, installed from the plugin
  source): semantic-search, local-titles, youtube-live, youtube-shorts, obs-tracker, discord-bot (on hold).
  `dev` plugins (`hello`, `hello-sandboxed`) are staged only by dev builds (`npm run tauri dev`,
  `npm run build:plugins:dev`).
- **No backwards compatibility** before the first public release: no data migrations, no shims —
  except the one QuadFlow 1.x piece (`quadflow-core/src/import_v1/`): import the 1.x project list,
  and move a 1.x `.quadflow/` aside to `.quadflow-v1-backup/` when such a project is opened.

## CLI

One binary: no args → GUI, any args → CLI (`src-tauri/src/main.rs`). Every command supports `--json`
and exits non-zero on failure. The CLI walks up from the cwd to `.quadflow/config.json`; there is no
implicit active project in the backend. Plugins can add subcommands (`quadflow <plugin-cmd>`, run via
their sidecar or an exec handler). `quadflow docs --list` / `quadflow docs <id>` prints agent docs;
`quadflow context …` manages the managed region of CLAUDE.md / AGENTS.md.

Safety: the user may run an installed QuadFlow. Never run the `quadflow` on PATH against real
projects for testing; use the built binary with `QUADFLOW_PROFILE=dev` and a temp
`QUADFLOW_DATA_DIR` (dev data goes to `.quadflow-dev/`). Tests set `QUADFLOW_SECRETS_BACKEND=memory`.

## Development

```bash
npm ci
npm run tauri dev          # full app (Vite + Rust), stages plugins first
npm run dev                # Vite only (no Tauri APIs)
npm run build              # release app + installer for this OS
npm run build:plugins      # build + stage first-party plugins into src-tauri/resources/plugins
npm run check              # ALL local checks (there is no hosted CI): agent-literal grep, tsc, web build,
                           # cargo check, core tests, sidecar SDK tests, bindings export + drift,
                           # plugin builds/tests, plugin docs, plugin index drift, release config, clippy
npm run test:e2e           # builds the dev exe, then runs the GUI e2e suite in scripts/ui/
```

Faster loops: `npx tsc --noEmit`; `cargo check -p quadflow-core --manifest-path src-tauri/Cargo.toml`;
`cargo test -p quadflow-core --manifest-path src-tauri/Cargo.toml`. Opt in to sccache with
`RUSTC_WRAPPER=sccache` (not forced by the repo). New checks go into `scripts/check.mjs`; never add
hosted CI workflows.

Conventions: LF line endings (also when writing files from scripts — tests `include_str!` working-tree
files); strict TypeScript (unused variables are errors); logic in `quadflow-core`, Tauri commands stay
thin; tests never touch the real user data dir (`quadflow_core::testing::{TempProject, TempApp}`).

### How much to test

Match verification to the change; the full gate is for releases.

- **Plugin-only change** (`plugins/<id>/`): build and test that plugin (`npm run build`, `npm test` in
  its folder), `node --test scripts/ui/<id>.test.mjs` against the existing dev exe if it has one.
  No app rebuild, no full suite. The `/plugin-dev` skill has the fast loop (incl. loading a dev copy
  into the running QuadFlow with hot reload).
- **Shared packages / app core**: `npm run check` plus the affected `scripts/ui/*.test.mjs`.
- **Releases**: `npm run release` runs `npm run check`; that plus the tests of what changed is the
  gate. Run the full `npm run test:e2e` only for broad core changes (layout, terminals, plugin host
  across many plugins, data layer) — not routinely before every release.

### GUI harness (verify UI changes in the real app)

`scripts/ui/` drives an isolated dev build over CDP (read `scripts/ui/README.md` first):
`npm run build:dev-exe`, then `node scripts/ui/cli.mjs launch`, drive it (`click`, `keys`, `text`,
`term`, `js`), `shot <png>` and view the screenshot, `close`. It uses a temp data dir and profile,
skips onboarding, and only ever kills the PID tree it started — never kill QuadFlow by name.

## Release

Releases are built locally with the generic `quadflow ship` pipeline driven by
`npm run release -- …` (`scripts/release.mjs`, config `scripts/release/ship.config.json`): version
bump across `package.json`, `tauri.conf.json` and both `Cargo.toml`, changelog, `npm run check`,
build, updater `latest.json` + signatures, plugin archives, tag, draft GitHub releases. Plugin
releases feed `plugins/index.json`. Details: `docs/RELEASING.md`.
