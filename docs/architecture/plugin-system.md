# Plugin system

Status: **binding design** for roadmap §2 "Plugin system" and §4 "Plugins to ship". Depends on
`data-layer.md` (core APIs, app DB tables, events, generated types). Agent providers are specified
in `agent-providers.md`; this doc defines the generic machinery they use.

---

## 0. Rules

1. **Every tool is a plugin.** The shell itself keeps only: layout/mosaic, terminal tiles, empty
   tiles, the agent-launch toolbar (driven by provider plugins), command palette, core settings
   pages (General, Appearance, Terminal, Agents, Plugins, Keyboard), onboarding.
2. **One registry.** Everything the shell shows for a tool (tile component, flyout, icon, group,
   default size, default config, config form, palette commands, toolbar buttons) comes from the
   plugin manifest + the plugin's UI module. No hand-maintained per-tool switch statements remain.
3. **Same API, two transports.** Trusted (first-party) plugins run in the host document and call
   the host API directly; sandboxed (third-party) plugins run in an iframe and call the same API
   over postMessage RPC. A plugin bundle works unchanged in both modes.
4. **Permissions are enforced in Rust.** Every privileged host-API method is dispatched through one
   Rust table that checks the calling plugin's granted permissions. JS-side checks are UX only.
5. **Sidecars never come from compile-time paths.** They are files inside the plugin directory,
   selected per platform from the manifest.

## 1. Terms

| Term | Meaning |
|---|---|
| Plugin | A directory with `quadflow-plugin.json` (+ UI bundle, assets, docs, optional sidecar). |
| Contribution | An entry in `contributes` (tile, toolbar item, command, …). Addressed as `<pluginId>/<contributionId>`. |
| Tile | A contribution renderable in a mosaic pane and/or a toolbar flyout. |
| Tool config | A row in `tool_configs` (data-layer.md §7): a user-visible, configurable "tool" pointing at a tile or toolbar contribution. |
| Tile instance | A row in `tile_instances`: one open tile in a workspace. Layout leaf id `tool:<instanceId>`. |
| Origin | `bundled` (shipped in app resources), `installed` (from a source), `dev` (loaded from a folder). |
| Isolation | `trusted` (same-context) or `sandboxed` (iframe). Decided by the host, never by the manifest (§8.1). |

Core validates manifests with this schema (`jsonschema` crate, draft 2020-12) **plus** semantic
checks in `plugins/manifest.rs`: every referenced file exists; `ui.entry` required if any tile,
settingsPage `custom`, or command without sidecar; command ids referenced by toolbar items and
context menus exist; `cliCommands[].name` not in the reserved set (`gui init doctor docs context
plugins ideas issues labels epics plans discovery scripts ship chat missions help version`) and
unique across enabled plugins; a bare id only from the official source or `bundled`; `agentProvider`
validated per agent-providers.md §3.

## 4. Locations, discovery, registry

### 4.1 Where plugins live

| Origin | Path | Writable | Notes |
|---|---|---|---|
| `bundled` | `<resource_dir>/plugins/<id>/` | no | first-party, built from `/plugins`, version = app version |
| `installed` | `<appData>/plugins/<id>/<version>/` | by core only | from a source; previous version kept for rollback |
| `dev` | any folder listed in setting `plugins.devPaths` | user | "Load unpacked"; hot reload |

There are **no per-project plugin installs** (a cloned repo must not be able to run code).
`ProjectConfig.recommendedPlugins` makes the shell offer "This project recommends: …" with the
normal install/consent flow.

Per-plugin data: `<appData>/plugin-data/<id>/` (private, created on first use). Project-scoped
plugin data: `.quadflow/plugins/<id>/` (shared) and `.quadflow/local/plugins/<id>/` (machine-local).

Resource dir resolution works the same in GUI and CLI (same executable):
`tauri::path::resource_dir` equivalent implemented in core `paths::resource_dir()` from
`current_exe()` (Windows/Linux: `<exe dir>/resources` for Tauri's layout; macOS:
`<exe>/../Resources`), overridable by `QUADFLOW_RESOURCE_DIR` (dev: `src-tauri/resources`).

### 4.2 Registry — `quadflow-core/src/plugins/registry.rs`

```rust
pub struct PluginRegistry { plugins: BTreeMap<String, LoadedPlugin> }
pub struct LoadedPlugin {
    pub manifest: Manifest,                 // parsed, validated
    pub root: PathBuf,                      // directory
    pub origin: PluginOrigin,               // Bundled | Installed | Dev
    pub isolation: Isolation,               // Trusted | Sandboxed (§8.1)
    pub status: PluginStatus,               // Active | Disabled | NeedsConsent | Incompatible{reason} | Failed{reason} | UnsupportedPlatform
    pub granted: BTreeSet<Permission>,
}
impl PluginRegistry {
    pub fn load(paths: &AppPaths, db: &AppDb) -> Result<Self>;   // bundled ∪ installed ∪ dev; DB state applied
    pub fn get(&self, id: &str) -> Option<&LoadedPlugin>;
    pub fn active(&self) -> impl Iterator<Item = &LoadedPlugin>;
    pub fn contributions(&self) -> Contributions;                // flattened, active plugins only
}
```

Resolution when the same id exists in several origins: `dev` > `installed` (if newer than bundled
and compatible) > `bundled`.

Status rules:
- `platforms` does not contain the current OS → `UnsupportedPlatform` (hidden from UI lists except
  "Show incompatible").
- `apiVersion` not satisfied → `Incompatible`. Compatibility: `semver::VersionReq::parse(apiVersion)`
  must match `PLUGIN_API_VERSION` **and** the requirement's major must equal the host major. The
  host implements exactly one API major.
- Manifest invalid / files missing → `Failed`.
- Requested permissions ⊄ granted → `NeedsConsent` (bundled plugins: granted automatically on
  first load, still listed in UI).
- DB `enabled = 0` → `Disabled`.

`PLUGIN_API_VERSION` is a const in `plugins/mod.rs` and in `packages/plugin-api/src/version.ts`
(CI test asserts equal).

Runtime-only fields (`needsAttention`, `isFlyoutInstance`, `status`) live in `toolStore`, not in
the DB.

Layout leaf ids (mosaic `MosaicNode<string>`), all prefixed — no more bare UUIDs:

| Leaf | Format |
|---|---|
| Terminal | `term:<terminalId>` |
| Tool tile | `tool:<tileInstanceId>` (ULID) |
| Empty | `empty:<ulid>` |
| Global workspace | `globalWs:<id>`; frame leaf `__project__` |

`src/lib/layoutIds.ts` owns `parseLeafId(id) -> { kind: 'term'|'tool'|'empty'|'globalWs'|'project', id }`;
every `startsWith('tool:')` in the tree is replaced by it.

Flyouts: a flyout is a `TileInstance` with `workspaceId` set and a runtime `isFlyoutInstance`
flag, not in the layout tree; `popFlyoutToPane` inserts its leaf id. Instances of a disabled or
uninstalled plugin render `<MissingPluginTile>` with "Enable"/"Install" actions instead of
crashing or vanishing.

### 5.3 Tool config sync

`domains/app/tool_configs.rs::tool_configs_sync_with_plugins(db, registry)` runs at startup, after
install/uninstall/enable/disable:
1. For each active plugin contribution with `defaultToolConfig` and no config having
   `auto_created = 1` for that `(plugin_id, contribution_id)`: insert one from the defaults.
2. Configs of uninstalled plugins: delete (instances cascade).
3. Configs of disabled/incompatible plugins: kept, hidden by the frontend.
Users can add more configs for tiles with `instanceMultiple: true` (e.g. several TUI tools).

### 5.5 Commands, menus, `when`

- Command ids are globally `<pluginId>/<commandId>`; core commands use `core/<id>`
  (`core/new-terminal`, `core/close-pane`, `core/switch-project`, `core/settings`,
  `core/launch-agent`, `core/layout-<preset>`, …).
- `core` is a real bundled plugin (`plugins/core`, "QuadFlow Core"): its manifest contributes the
  Terminal and AI Agent toolbar items, the session History flyout (`core/chat-history`) and the
  commands `core/new-terminal` / `core/launch-agent`. It is *internal*: its UI module
  (`src/plugins/core/`) ships in the host bundle (`INTERNAL_MODULES` in `loader.ts`, bundled copy
  only; `ui.entry` is a stub) because it drives the shell's stores. `ctx.commands.execute('core/…')`
  runs its commands like any other plugin's. Palette-only shell entries (`core/open:<id>`,
  `core/launch-agent:<provider>`) are palette ids, not executable commands.
- Each tile gets an automatic `core/open:<toolConfigId>` palette command.
- Shortcuts: manifest `shortcut` is a default; user overrides in setting `shell.keybindings`.
  Conflicts: core wins, then first-enabled plugin; Settings → Keyboard shows conflicts.
- `when` expressions: `&&`, `||`, `!`, parentheses over context keys `project`, `workspace`,
  `terminal`, `terminal.agent`, `terminal.provider == 'codex'`, `tile.plugin == 'issues'`,
  `platform == 'windows'`, `selection`. Parsed by `contextKeys.ts`; unknown keys are false.
- Palette entity search (issues/ideas/plans) moves into the owning plugins via an optional UI
  module export `paletteProviders: { search(query, ctx): Promise<PaletteItem[]> }`, declared in the
  manifest as `contributes.paletteProviders: [{ id, title }]` so the shell knows which plugins to load
  for a query (MIG-ideas, §17).

### 6.8 Versioning

- `@quadflow/plugin-api` follows semver; `PLUGIN_API_VERSION` is the implemented version.
- Minor = additive (new methods/fields/topics). Major = breaking; the host supports one major.
- Plugins needing a newer minor feature-detect with `ctx.api.has('agents.launch')` or declare
  `apiVersion: "^1.3.0"`.
- The npm package version equals `PLUGIN_API_VERSION`; generated domain types are part of the
  API (a breaking change in a core struct is a major bump; adding optional fields is minor).

```rust
pub struct HostEnv { pub core: Arc<Core>, pub extensions: Vec<Arc<dyn HostExtension>> }
pub trait HostExtension: Send + Sync { fn methods(&self) -> &[MethodSpec]; }
pub fn dispatch(env: &HostEnv, call: HostCall) -> Result<serde_json::Value, CoreError>;
```

`dispatch`: look up method (unknown → `invalid_input`), compute required permission, check
`plugin.granted` (missing → `permission_denied` with the permission string), check plugin status
`Active`, run handler with `Actor::plugin(id)`, log `(plugin, method, ok/err, ms)` at debug.

Core registers: `data.*` (all of §6.3), `storage.*`, `settings.*`, `secrets.*`, `fs.*`,
`shell.exec`, `shell.openExternal`, `http.fetch`, `log.*`, `project.list`. The Tauri app adds a
`HostExtension` (`src-tauri/src/plugin_host/`) for `terminals.*`, `agents.*`, `notifications.system`,
`clipboard.*`, `native.*`, `ui.pickFile` (dialogs), because those need the app handle.

The same table serves: `plugin_invoke` (UI, both trust modes), sidecar → host requests (§10.4),
and CLI-mode sidecars (§9.2).

Subscriptions (`terminals.onData`, `data.onDidChange`, `fs.watch`, `shell.spawn`) go through
`plugin_subscribe(pluginId, topic, params, Channel)` with the same permission checks; Rust pushes
into the `Channel`, the host forwards to the plugin.

### 7.2 JS side

| API group | Trusted (same document) | Sandboxed (iframe) | Permission (Rust) |
|---|---|---|---|
| project, workspace, events (host topics), ui.theme, overlay, commands, ui.openTile/confirm/prompt | host JS stores directly | RPC → host JS | none (UI-local) |

## 8. Loading and isolation

### 8.1 Isolation decision

| Origin | Isolation |
|---|---|
| `bundled` | trusted |
| `installed` from the built-in official source with a bare id | trusted |
| `installed` from any other source | sandboxed |
| `dev` | sandboxed; trusted only when the dev path is inside a checkout that contains `plugins/<id>` of this repo **and** setting `plugins.devTrusted = true` (for first-party development) |

The manifest has no field to request trust.

### 8.2 Asset protocol

`src-tauri/src/plugin_protocol.rs` registers
`register_asynchronous_uri_scheme_protocol("qfplugin", handler)`. URLs are built with Tauri's
`convertFileSrc(<logical path>, 'qfplugin')`, giving `http://qfplugin.localhost/<path>` on
Windows and `qfplugin://localhost/<path>` on macOS/Linux. Logical paths:

| Path | Served from |
|---|---|
| `/<pluginId>/<relPath>` | plugin root of the resolved origin (only files under it; percent-decoded; `..`, absolute, backslash rejected; symlinks resolved and re-checked) |
| `/_runtime/<file>` | `<resource_dir>/plugin-runtime/` (sandbox runtime, §8.4) |
| `/_frame/<pluginId>` | generated frame HTML for a sandboxed plugin (§8.4) |

Responses: correct `Content-Type` by extension, `Cache-Control: no-cache` for `dev`,
`Access-Control-Allow-Origin: *` (module scripts from an opaque-origin frame need CORS),
`X-Content-Type-Options: nosniff`. Disabled/unknown plugins → 404.

CSP (`tauri.conf.json` `app.security.csp`):

```
default-src 'self';
script-src 'self' qfplugin: http://qfplugin.localhost;
style-src 'self' 'unsafe-inline' qfplugin: http://qfplugin.localhost https://fonts.googleapis.com;
img-src 'self' data: blob: qfplugin: http://qfplugin.localhost;
font-src 'self' data: qfplugin: http://qfplugin.localhost https://fonts.gstatic.com;
frame-src qfplugin: http://qfplugin.localhost;
connect-src 'self' ipc: http://ipc.localhost;
worker-src 'self' blob:
```

(Remote network access by plugins goes through `http.fetch` in Rust, never `connect-src`.)

### 8.3 Trusted (first-party) loading — shared modules via import map

The host shares one copy of React and the QuadFlow packages with trusted plugins.

1. `index.html` contains, before any module script:

```html
<script type="importmap">
{ "imports": {
  "react": "/qf-shared/react.js",
  "react/jsx-runtime": "/qf-shared/react-jsx-runtime.js",
  "react-dom": "/qf-shared/react-dom.js",
  "react-dom/client": "/qf-shared/react-dom-client.js",
  "zustand": "/qf-shared/zustand.js",
  "@quadflow/plugin-api": "/qf-shared/plugin-api.js",
  "@quadflow/ui": "/qf-shared/ui.js"
} }
</script>
```

2. `src/main.tsx` first statement (before rendering): `installSharedModules()` sets
   `globalThis.__QUADFLOW_SHARED__ = { react: React, 'react/jsx-runtime': jsxRuntime, 'react-dom': ReactDOM,
   'react-dom/client': ReactDOMClient, zustand, '@quadflow/plugin-api': pluginApiTrusted, '@quadflow/ui': ui }`.
3. `public/qf-shared/*.js` are **generated** by `scripts/gen-shared-shims.mjs` (run by
   `predev`/`prebuild`): for each specifier it imports the real module in Node, enumerates export
   names and writes
   `const m = globalThis.__QUADFLOW_SHARED__["react"]; export default m.default ?? m; export const { useState, useEffect, … } = m;`.
   The generator fails the build if a plugin bundle imports a name the shim does not export
   (checked by `@quadflow/plugin-build`).
4. Loader (`src/plugins/loader.ts`): `const mod = (await import(/* @vite-ignore */ pluginUrl(id, manifest.ui.entry) + devBust)).default as PluginModule`;
   inject `manifest.ui.style` as `<link rel="stylesheet">`; call `activate(ctx)` per manifest
   `activation`; register commands; tiles are rendered by `TileHost` as normal React children
   (shared React ⇒ context, hooks, portals work).
5. Plugin bundles **must** externalize exactly the import-map specifiers (enforced by
   `@quadflow/plugin-build`); they bundle everything else (dnd-kit, codemirror, xterm addons …).

`@quadflow/plugin-api` in trusted mode is a thin module that throws if used outside a context:
all functionality is reached through the `ctx` object passed to components/activate; the module
exports only `definePlugin`, types and constants. (So the same import works in both modes.)

### 8.4 Sandboxed (third-party) loading — iframe + postMessage RPC

- `packages/plugin-runtime` builds to `src-tauri/resources/plugin-runtime/`: ESM builds of react,
  react-dom, zustand, `@quadflow/ui`, and `plugin-api.js` = the **RPC client** implementation.
- `/_frame/<pluginId>?role=tile&tile=<tileId>&instance=<instanceId>` returns HTML with an import
  map pointing the same specifiers at `/_runtime/*.js`, the `@quadflow/ui` CSS, current theme CSS
  variables inline, and a bootstrap that imports `/<pluginId>/<ui.entry>`, waits for the host
  `init` message, then renders `tiles[tile]` (or runs `activate`/`commands` for `role=background`).
- The host creates `<iframe sandbox="allow-scripts allow-forms allow-popups-to-escape-sandbox"
  src=…>` — **no `allow-same-origin`** (opaque origin: no access to host DOM, storage, cookies,
  or other plugins' frames). One `role=background` frame per active sandboxed plugin hosts
  `activate()` and command handlers; one frame per tile instance.
- RPC messages (all carry `qf: 1`):

```ts
type ToHost =
  | { qf: 1; kind: 'req'; id: number; method: string; params?: JsonValue }      // method = "data.issues.list", "ui.confirm", ...
  | { qf: 1; kind: 'sub'; id: number; topic: string; params?: JsonValue }       // "terminals.onData", "events.on", ...
  | { qf: 1; kind: 'unsub'; id: number }
  | { qf: 1; kind: 'ui'; op: 'setTitle' | 'setState' | 'setAttention' | 'close' | 'resize'; value?: JsonValue }
  | { qf: 1; kind: 'ready' }
type ToFrame =
  | { qf: 1; kind: 'init'; plugin: {...}; api: {...}; project: ProjectInfo | null; workspace: {...} | null; settings: Record<string, JsonValue>; theme: ThemeSnapshot; tile?: TileProps-serializable }
  | { qf: 1; kind: 'res'; id: number; result?: JsonValue; error?: CoreError }
  | { qf: 1; kind: 'evt'; id: number; payload: JsonValue }                      // subscription event
  | { qf: 1; kind: 'ctx'; project?: ...; workspace?: ...; theme?: ...; settings?: ...; visible?: boolean }
```

- Host bridge (`src/plugins/rpcBridge.ts`): one `message` listener; identifies the plugin by
  `event.source === frame.contentWindow` from its frame registry (the frame cannot claim another
  id); ignores messages without `qf: 1`; enforces 4 MiB per message and 200 in-flight requests per
  frame; maps `req.method` to the host context functions of §7.2 (unknown → error). Binary data
  (`Uint8Array`) is transferred via structured clone.
- Frames get theme updates through `ctx` messages; overlay geometry is not exposed (no native APIs
  in sandbox; `native:*` permissions are refused for sandboxed plugins at install).

## 9. CLI contributions and agent context docs

### 9.1 Dispatch

The clap root in `cli/mod.rs` sets `allow_external_subcommands = true`. For an unknown
subcommand `quadflow <name> <args…>`:
1. Load `PluginRegistry` read-only (bundled + installed + dev from the app DB; the CLI never
   writes plugin state except via `quadflow plugins …`).
2. Find an active plugin with `cliCommands[].name == name` (uniqueness enforced at enable time).
   None → clap-style "unrecognized subcommand" + list of plugin commands, exit 2.
3. Run the handler (§9.2) with:
   - env: `QUADFLOW_CLI=<path of current exe>`, `QUADFLOW_PROJECT_DIR=<resolved root or empty>`,
     `QUADFLOW_PLUGIN_ID`, `QUADFLOW_PLUGIN_DIR`, `QUADFLOW_PLUGIN_DATA`, `QUADFLOW_JSON=0|1`,
     plus inherited actor vars.
   - argv: everything after `<name>` (global `--json` / `--project` are consumed by core and
     re-exported via env).
4. Exit code = handler's exit code.

`quadflow docs --list` and `quadflow --help` include plugin commands with their `summary`.

### 9.2 Handler types

- `exec`: spawn `binaries[<os>-<arch>]` from the plugin dir directly (argv, no shell), stdio
  inherited. The binary uses `$QUADFLOW_CLI … --json` for any data access (so it needs no
  library). Permissions: an exec handler runs with the user's privileges — therefore `exec`
  handlers are allowed only for **trusted** plugins; sandboxed plugins must use `sidecar`.
- `sidecar`: the CLI process starts a private instance of the plugin's sidecar (same binary/entry
  as §10) with env `QUADFLOW_SIDECAR_MODE=cli`, performs `initialize`, sends request
  `cli/run { argv, cwd, json, projectRoot }`, prints `cli/output { stream, text }` notifications to
  stdout/stderr as they arrive, waits for the result `{ exitCode }`, sends `shutdown`/`exit`.
  Sidecar → host requests are served by the CLI process through the same dispatch table (§7.1)
  with the plugin's granted permissions (read from the app DB). Terminal/agent/native methods are
  unavailable in CLI mode (`unsupported`).

### 9.3 Agent context docs

The context-module registry (`quadflow-core/src/context/registry.rs`) is built from:
- the core doc `quadflow` (bundled `src-tauri/resources/agent-context/quadflow.md`: what the CLI
  is, `quadflow docs`, project discovery, `--json` envelope, exit codes), always enabled;
- every **active** plugin's `agentContextDocs`: module id = `<pluginId>` if the doc id equals the
  plugin id, else `<pluginId>.<docId>`; content read from the plugin dir.

`quadflow docs <module>` prints any registered module; `quadflow context enable|disable <module>`
edits `ProjectConfig.agentContext.modules`; writing the managed regions into the provider context
files (`CLAUDE.md`, `AGENTS.md`, …) is specified in agent-providers.md §7. On plugin enable, docs
with `default: true` are suggested (toast "Add Issues docs to this project's agent context?"),
never silently added to a git-tracked file.

## 10. Sidecar protocol

### 10.1 Transport

- JSON-RPC 2.0 over the child's **stdin/stdout**, framed as **NDJSON**: one JSON object per line,
  UTF-8, `\n` terminated, no embedded newlines (JSON escapes them), max 16 MiB per line (longer →
  protocol error, sidecar restarted). Batches are not used.
- **stderr** is captured line-by-line into `<appData>/logs/plugins/<id>.log` (rotated at 5 MiB ×3)
  and the last 200 lines are kept in memory for the Plugins settings page.
- Generalizes `discord_bridge.rs` (NDJSON, `type`-tagged messages) into standard JSON-RPC ids,
  errors and notifications.

### 10.2 Process lifecycle — `quadflow-core/src/plugins/sidecar/`

```rust
pub struct SidecarSupervisor { /* per plugin: state, child, pending requests, backoff */ }
pub enum SidecarState { Stopped, Starting, Running, Restarting { attempt: u32 }, Failed { reason: String } }
impl SidecarSupervisor {
    pub fn request(&self, plugin: &str, method: &str, params: Value, timeout: Duration) -> Result<Value, CoreError>;
    pub fn notify(&self, plugin: &str, method: &str, params: Value) -> Result<(), CoreError>;
    pub fn subscribe(&self, plugin: &str, f: Box<dyn Fn(&str, &Value) + Send + Sync>) -> SubscriptionId;
    pub fn stop(&self, plugin: &str);  pub fn stop_all(&self);   // app exit
}
```

- Resolution: `binaries["<os>-<arch>"]` (`os` ∈ windows|macos|linux, `arch` ∈ x86_64|aarch64);
  missing → plugin `Failed("no sidecar for this platform")`. `runtime: node` → `node` from PATH
  (`which`), requires permission `sidecar:runtime:node`; missing node → `Failed` with install hint.
  On macOS/Linux the binary must be executable; core `chmod +x` after install.
- Spawn: `std::process::Command` (argv, no shell), cwd = plugin data dir, env = manifest `env` +
  `QUADFLOW_PLUGIN_ID/DIR/DATA`, `QUADFLOW_SIDECAR_MODE=gui|cli`; Windows `CREATE_NO_WINDOW`,
  and the child is assigned to a Job Object with `KILL_ON_JOB_CLOSE` (dies with the app); Unix:
  own process group, `prctl(PR_SET_PDEATHSIG)` on Linux.
- Start: `activation: onStartup` → at plugin activation; `onDemand` → on first
  request/notify/subscription.
- Handshake: host → `initialize` (timeout 10 s); sidecar replies; host → `initialized`
  notification; state `Running`. Requests issued during `Starting` are queued.
- Crash (exit while not stopping, or protocol error): fail pending requests with
  `external: sidecar exited`; if `restart: onCrash`, restart after backoff 1 s, 2 s, 4 s, 8 s,
  16 s, 30 s, 60 s (cap); more than 5 crashes within 5 minutes → `Failed` (UI shows "Restart"
  button, `sidecar.restart()`). A successful 10-minute run resets the counter.
- Stop (plugin disable/uninstall/update, app exit): `shutdown` request (timeout 3 s) → `exit`
  notification → wait 2 s → kill the job/process group.
- Default request timeout 30 s; `request(…, timeout)` overrides; `$/cancelRequest
  { id }` notification sent on timeout or when the UI caller is disposed.

### 10.3 Host → sidecar methods

| Method | Kind | Params → Result |
|---|---|---|
| `initialize` | request | `{ protocolVersion: 1, host: { version, apiVersion, platform, arch, mode: 'gui'|'cli' }, plugin: { id, version, dir, dataDir }, project: { root, rootKey } \| null, settings: {…}, locale }` → `{ capabilities?: { cli?: boolean; agentProvider?: boolean } }` |
| `initialized` | notification | `{}` |
| `shutdown` | request | `{}` → `null` |
| `exit` | notification | `{}` |
| `settings/didChange` | notification | `{ key, value }` |
| `project/didChange` | notification | `{ root, rootKey } \| null` |
| `cli/run` | request | `{ argv: string[], cwd, json: boolean, projectRoot: string \| null }` → `{ exitCode: number }` |
| `agentProvider/*` | request | agent-providers.md §4.3 |
| `$/cancelRequest` | notification | `{ id }` |
| any other method | request/notification | plugin-defined, forwarded from the plugin UI via `ctx.sidecar.request/notify` (must not start with `$/`, `host/`, `cli/`, `ui/`, `initialize`, `shutdown`, `exit`) |

### 10.4 Sidecar → host methods

| Method | Kind | Notes |
|---|---|---|
| `host/call` | request | `{ method, params }` → result of `dispatch()` (§7.1) with the plugin's permissions — same API surface as the UI (e.g. `data.issues.create`, `storage.get`, `http.fetch`, `notifications.system`) |
| `host/log` | notification | `{ level, message }` → plugin log |
| `host/emit` | notification | `{ topic, payload }` → `events` as `<pluginId>:<topic>` |
| `ui/<anything>` | notification | delivered to the plugin's UI `ctx.sidecar.onNotification('<anything>', …)` (all its tiles/background) |
| `cli/output` | notification | `{ stream: 'stdout' \| 'stderr', text }` (CLI mode) |

### 10.5 UI ↔ sidecar

`ctx.sidecar.request(m, p)` → `plugin_sidecar_request(pluginId, m, p)` → supervisor → JSON-RPC
request; response returned. Sidecar `ui/*` notifications are emitted as a Tauri event
`plugin-sidecar` `{ pluginId, method, params }` to the main window; the host routes them to the
plugin's subscribers (and into frames for sandboxed plugins). A plugin's UI can talk only to its
own sidecar.

### 10.6 Reference implementations

`packages/sidecar-sdk-rust` (crate `quadflow-sidecar`, workspace member): NDJSON framing,
`Server::new().on_request("x", handler).run()`, `host.call(method, params)`. A ~150-line Node
helper ships in `create-quadflow-plugin` templates. The Discord plugin (on hold) is the
reference conversion of `discord_bridge.rs`: its `init`/`create_thread`/`output`/`close_thread`/
`update_settings`/`shutdown` messages become JSON-RPC methods `discord/init`, …; replies become
`ui/reply` notifications; the bot token moves to `secrets`.

### 11.1 List

| Permission | Grants | Risk shown |
|---|---|---|
| `data:<domain>:read` (`ideas issues plans discovery scripts ship chat missions`) | read that domain in any registered project | low |
| `data:<domain>:write` | read + write that domain (implies read) | medium |
| `project:config:write` | edit `.quadflow/config.json` | medium |
| `terminal:spawn` | create terminals it owns (read/write/kill them) | high |
| `terminal:io` | read/write **any** terminal (incl. agent sessions) | high |
| `agents:read` | list providers, models, detection | low |
| `agents:launch` | start agent CLIs in terminals | high |
| `fs:read:project` / `fs:write:project` | files under the current project root | medium / high |
| `fs:read:home` / `fs:write:home` | files under the user's home | high |
| `fs:read:any` / `fs:write:any` | any path | critical |
| `shell:exec:<program>` | run `<program>` (basename, no extension; resolved from PATH) with argv | high |
| `shell:open-external` | open http(s)/mailto URLs in the browser | low |
| `network:<host>[:port]` / `network:*` | `http.fetch` to that host (exact match; `*.` prefix not allowed — list each) / any host | medium / high |
| `notifications` | OS notifications | low |
| `clipboard:read` / `clipboard:write` | clipboard | medium / low |
| `secrets` | OS keychain entries namespaced to the plugin | medium |
| `native:windows` | main window handle, tile geometry (embed native windows) | critical |
| `native:webview` | child webviews in tiles | high |
| `native:screen-capture` | capture screen regions | high |
| `sidecar:runtime:node` | run its sidecar with the system `node` | medium |

Implicit, no permission: own `storage`, own `settings`, own plugin data dirs (`pluginData`,
`projectPluginData`, `projectPluginLocal` fs scopes), own sidecar, `log`, UI APIs, `events`.

Sandboxed plugins may not hold `native:*`, `terminal:io`, `fs:*:any`; install is refused.

### 11.2 Consent UX

- Install / first enable: dialog listing the plugin, source, version, and permissions grouped by
  risk with human descriptions (from `permissions.rs::describe()`), "Install" / "Cancel".
  Critical permissions need an extra checkbox "I trust this plugin".
- Update adding permissions: update is downloaded, the plugin keeps running the old version, the
  Plugins page shows "Update needs approval: + network:api.example.com". Approve → switch;
  decline → stay. Removed permissions are revoked automatically.
- Settings → Plugins → <plugin> → Permissions shows granted permissions; any can be revoked (plugin
  goes to `NeedsConsent` if a declared one is revoked).
- Bundled plugins: permissions auto-granted, displayed read-only.

### 11.3 Enforcement point

`plugins::host::dispatch` (§7.1) for every call from UI (both modes), sidecars and CLI-mode
sidecars; `plugin_subscribe` for streams; the asset protocol only serves files of active plugins.
`fs` handlers canonicalize (`dunce`) and verify the result is inside the scope root (rejecting
symlink escapes). `shell.exec` resolves the program with `which` and checks the permission against
the requested basename before resolution.

## 12. Plugin sources

### 12.1 Source URLs

- `github:OWNER/REPO[#REF][:PATH]` → `https://raw.githubusercontent.com/OWNER/REPO/REF/PATH`
  (`REF` default `HEAD`, `PATH` default `index.json`).
- Any `https://…/index.json` URL. (No `http:`; no file URLs except dev.)
- Built-in source (`builtin = 1`, cannot be removed, can be disabled):
  `github:HardHeadHackerHead/QuadFlow:plugins/index.json` (OWNER from the single constant
  `quadflow_core::urls::REPO`, overridable by `QUADFLOW_PLUGIN_INDEX_URL`).

### 12.2 `index.json` schema (`packages/plugin-api/schema/plugin-index.schema.json`)


Archive format: `.zip` whose root contains `quadflow-plugin.json`. Plugins with sidecars publish
one archive per `os-arch` (`url` with `{os}-{arch}`); UI-only plugins publish one archive.

### 12.3 Flows (`quadflow-core/src/plugins/sources/`)

- **Refresh**: GET index with `If-None-Match: <etag>` (10 s timeout, 5 MiB cap), validate schema,
  store `etag`, `last_checked_at`, cache body at `<appData>/cache/sources/<sourceId>.json`.
  Errors are stored in `last_error` and shown; a failing source never blocks others.
- **Install(source, id, version?)**: choose the highest version with matching platform and
  compatible `apiVersion` (or the requested one) → build `InstallPlan { pluginId, version, url,
  sha256, size, permissions, isolation }` → UI consent → `plugins_install_confirm` → download to
  `<appData>/plugins/<id>/.download-<ulid>.zip` streaming SHA-256 and enforcing `size` (and a
  200 MiB hard cap) → mismatch → delete + `CoreError::Integrity` → extract to
  `<id>/<version>.staging/` rejecting absolute paths, `..`, drive prefixes, symlink entries, and
  >10 000 entries → validate manifest (`id`/`version` must equal the index entry, permissions
  must equal the index's list) → rename to `<id>/<version>/` → upsert `plugins` row (origin
  installed, granted = approved permissions) → registry reload → `tool_configs_sync_with_plugins`
  → activate.
- **Update check**: 30 s after startup, then every 24 h, and on demand: for each installed plugin
  find a newer compatible version in its source; store `available_update`; badge in toolbar and
  Settings → Plugins. Bundled plugins are updated only if the built-in index lists a newer
  version for the running app's API major (`bundled: true` entries).
- **Update**: as install into `<id>/<newVersion>/`; permission diff = new − granted; empty → stop
  sidecar, deactivate, switch `install_path`, reactivate; non-empty → `NeedsConsent` flow (§11.2).
  Keep exactly one previous version directory for rollback (`plugins_rollback(id)`); delete older.
- **Uninstall**: deactivate (unmount tiles, stop sidecar), delete `<appData>/plugins/<id>/`,
  delete `plugins` row, `plugin_kv` rows, `settings` namespace `plugin:<id>`, keychain entries
  `plugin:<id>:*`, tool configs (cascade instances); if `deleteData`, delete
  `<appData>/plugin-data/<id>/` (project-scoped `.quadflow/plugins/<id>/` is never auto-deleted).
  Bundled plugins cannot be uninstalled (only disabled).

CLI: `quadflow plugins list|info <id>|enable <id>|disable <id>|install <id> [--source <id>]
[--version v] [--yes]|update [<id>]|uninstall <id> [--delete-data]|sources list|sources add <url>|
sources remove <id>|sources refresh`. `install`/`update` without `--yes` print the permission list
and require confirmation on a TTY; non-TTY without `--yes` → exit 2.

## 15. Building, bundling, authoring

### 15.1 `@quadflow/plugin-build`

`defineQuadflowPlugin({ root })` returns a Vite config: library mode, `formats: ['es']`, entry
`src/index.tsx`, `fileName: 'index'` → `dist/index.js` (+ `dist/index.css`),
`rollupOptions.external` = the import-map specifiers (§8.3) exactly, `build.target: 'es2022'`,
`cssCodeSplit: false`, React plugin. A post-build step validates the manifest against the schema,
checks referenced files exist, checks that imported names from shared specifiers are exported by
the shims, and computes `dist/.integrity.json` (sha256 per file, for CI reproducibility).

Each `plugins/<id>/package.json`: `"scripts": { "build": "vite build", "dev": "vite build --watch" }`,
devDependency `@quadflow/plugin-build`, dependencies `@quadflow/plugin-api`, `@quadflow/ui` as
`workspace:*` peer-style (externalized).

### 15.2 Bundling into the app

- `npm run build:plugins` = `npm run build --workspaces --if-present` for `packages/*` then
  `plugins/*`, then `node scripts/bundle-plugins.mjs`, which copies for each plugin:
  `quadflow-plugin.json`, `dist/`, `assets/`, `docs/`, and sidecar binaries for the **current**
  target (`bin/<os>-<arch>/…` produced by `cargo build -p <plugin>-sidecar --release`) into
  `src-tauri/resources/plugins/<id>/`, and the sandbox runtime into
  `src-tauri/resources/plugin-runtime/`.
- `tauri.conf.json` `bundle.resources`: `resources/plugins/**/*`, `resources/plugin-runtime/**/*`,
  `resources/agent-context/**/*`, `resources/claude-template/**/*` (template content is owned by the
  claude-code plugin later; see agent-providers.md §9). `beforeBuildCommand`:
  `npm run build:plugins && npm run build:web`; `beforeDevCommand`: `npm run build:plugins && npm run dev`.
- Optional heavy plugins (`semantic-search`, `local-titles`) are **not** bundled; they are
  installed from the official source. Their sidecar crates are workspace members excluded from
  `default-members`, built only in their release CI jobs.
- `plugins/index.json` is generated in CI by `scripts/gen-plugin-index.mjs` from manifests and the
  release assets (`plugin-<id>-v<version>` GitHub releases with `<id>-<version>[-<os>-<arch>].zip`
  and sha256s). Never hand-edited.

### 15.3 Authoring

- `npm create quadflow-plugin@latest` (package `create-quadflow-plugin`): templates `tile`
  (React tile + settings), `tile-sidecar-rust`, `tile-sidecar-node`, `cli-command`, `agent-provider`.
- Dev mode: Settings → Plugins → "Load unpacked…" (or `quadflow plugins dev add <dir>`) → adds
  folder to `plugins.devPaths`; the host watches `<dev>/quadflow-plugin.json`, `<dev>/dist/**` and
  the sidecar files (notify, 300 ms debounce) → event `plugin-dev-changed` → the shell's registry
  `reload(id)`: deactivate, re-import with `?v=<now>`, remount tiles (instance state is preserved
  via `tile_instances.state`); the host restarts the sidecar if its binary/entry changed.
- `quadflow plugins validate <dir>` (core CLI) runs manifest + file checks.
- Docs: `docs/plugins/` (author guide; `manifest-reference.md` generated from the schemas) and an
  API reference generated from `@quadflow/plugin-api` with TypeDoc (`npm run docs:api`) — PL-10.
